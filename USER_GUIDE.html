Accounting & Receivables Management SaaS Platform

1. Project Overview

RECO is an Accounting & Receivables Management SaaS platform designed for Indian businesses. It provides double-entry bookkeeping, invoice management, receivables tracking, GST tax compliance, and financial reporting.

The application includes a web admin panel and a REST API at /api/v1/* with matching functionality for mobile apps.

Production Ready Web admin, REST API, journal posting, 9 financial reports, and Swagger docs at /api/documentation. User guide at /user-guide.
📊

Double-Entry Accounting

Full ledger engine with running balances, 5 account types, 6 voucher types

📱

Mobile API + Offline Sync

REST API with Sanctum auth, offline queue sync, manual sync button, and delta download when back online

🔔

Notifications & Support

In-app notifications plus ticket-based chat between tenant admin and SuperAdmin support team

🏢

Multi-Tenant

Company-based isolation. Each company has its own data, users, and settings

3.2 Multi-Tenancy

RECO uses a shared-database, shared-schema multi-tenancy approach. Every table includes a company_id column. All queries are automatically scoped to the authenticated user's company:

  • Each Company has its own users, accounts, parties, vouchers, reports, and settings
  • Companies are registered via the public website and require SuperAdmin approval
  • A SuperAdmin role manages all companies, plans, themes, and CMS content
  • Users within a company are assigned roles (Admin, Manager, Accountant, Viewer)

5. Installation & Setup

Prerequisites

  • PHP 8.3+
  • MySQL 8.x
  • Composer 2.x
  • Node.js 18+ & npm

Quick Setup

  1. Clone the repository 
    git clone <repo-url>
cd Reco
  2. Run setup script (installs dependencies, creates DB, builds assets) 
    composer setup

    This single command runs: composer install → copy .env → php artisan key:generate → php artisan migrate → npm install → npm run build

  3. Configure .env 
    DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3307
DB_DATABASE=laravel_onlinefirstman
DB_USERNAME=root
DB_PASSWORD=
  4. Seed the database (creates default roles, permissions, accounts) 
    php artisan db:seed
  5. Start development server 
    composer dev

    Starts 4 services concurrently: PHP server (port 8000), Queue worker, Log viewer (Pail), and Vite dev server

6. Login & Registration

Web Panel Login

  1. Visit /admin/login
  2. Enter email and password
  3. After login, redirected to /admin/dashboard

Company Registration Flow

  1. Visit /register on the public website
  2. Fill company details (name, GST, PAN, address, etc.)
  3. Fill admin user details (name, email, password)
  4. Submit → Company status set to "pending"
  5. SuperAdmin approves the company from /admin/companies/approval
  6. After approval, the company admin can log in and start using the system

API Authentication

The API uses Laravel Sanctum for token-based authentication:

POST /api/v1/login
Body: {
  "email": "user@example.com",
  "password": "password",
  "device_id": "android-abc123",
  "device_type": "android",
  "device_name": "Samsung Galaxy S24",
  "device_os": "Android 14",
  "fcm_token": "firebase-token..."
}
Response: { "token": "1|abc123...", "user": { ... } }

All subsequent requests:
Authorization: Bearer 1|abc123...

Device fields on login are optional but recommended for mobile apps — they register the device for offline sync tracking and push notifications. You can also call POST /api/v1/devices/register after login when the FCM token refreshes.

Additional API auth features: PIN login, app lock toggle, biometric auth, device management.

Voucher Lifecycle

  1. Create - User fills voucher form with lines (status: draft)
  2. Store - Voucher is saved to database but NOT yet in ledger
  3. Post - System validates debit=credit, generates ledger entries via LedgerService::generateForVoucher(), status becomes posted
  4. Cancel (optional) - Reverses ledger entries, status becomes cancelled

How Ledger Entries Are Generated

When a voucher is posted, LedgerService::generateForVoucher():

  1. Iterates through each voucher_line
  2. For each line, creates a record in the ledgers table with:
    • debit / credit values from the line
    • running_balance calculated based on account type's normal balance
    • balance_type set to debit or credit
  3. Running balance formula depends on account type:
    • Debit-normal (Asset/Expense): running_balance = previous_balance - credit + debit
    • Credit-normal (Liability/Income/Equity): running_balance = previous_balance + credit - debit
Important A voucher cannot be posted unless total_debit == total_credit (double-entry validation). Always ensure your lines balance before posting.

Workflow

  1. Create invoice at /admin/sales-invoices/create
  2. Add line items (item, quantity, rate, tax)
    • Items are looked up from items table
    • Tax is calculated using tax_rates table
    • Total = sum of (qty × rate) + tax
  3. Save invoice (status: draft)
  4. Record payment via /admin/sales-invoices/{id}/payment
  5. Once fully paid, status becomes paid
  6. If past due date and unpaid, status becomes overdue
  7. Overdue invoices visible at /admin/sales-invoices/overdue
Voucher Auto-Generation When a sales invoice is paid or sent, you can generate an income voucher automatically. This posts the transaction to the ledger (debit: AR 1250 / Party, credit: Sales Income).

17.1 Profit & Loss Statement

Purpose Shows income, expenses, and net profit/loss for a selected financial year. This is the primary performance report for any business.

Tables Used

Table How It's Used
accounts Fetch all active accounts where account_type = 'income' OR account_type = 'expense'
ledgers Get running balance for each income/expense account via LedgerService::getAccountBalance()
Filtered by: company_id, account_id, financial_year_id
Uses the last ledger entry for each account to get running_balance and balance_type

Generation Logic (Step by Step)

  1. ReportService::getProfitLoss(financial_year_id) is called
  2. Queries accounts table: WHERE company_id = ? AND account_type IN ('income', 'expense') AND is_active = 1
  3. For each income account, calls LedgerService::getAccountBalance() to get the credit balance
  4. For each expense account, calls LeadgerService::getAccountBalance() to get the debit balance
  5. getAccountBalance() queries the ledgers table for the last entry of that account within the FY: SELECT * FROM ledgers WHERE company_id = ? AND account_id = ? ORDER BY transaction_date DESC, id DESC LIMIT 1
  6. Total Income = sum of all income balances (credit normal)
  7. Total Expense = sum of all expense balances (debit normal)
  8. Net Profit/Loss = Total Income − Total Expense
  9. Positive = Profit, Negative = Loss

What the Report Shows

Section Content
Income Accounts Each income account with name, code, and amount
Total Income Sum of all income
Expense Accounts Each expense account with name, code, and amount
Total Expense Sum of all expenses
Net Profit/Loss Income − Expense. Highlighted as profit (green) or loss (red)
Financial Year The FY this report covers

Filters

Filter Default Options
financial_year_id Current FY Any financial year from financial_years table

17.2 Balance Sheet

Purpose Shows assets, liabilities, and equity for a financial year. Demonstrates the fundamental accounting equation: Assets = Liabilities + Equity.

Tables Used

Table How It's Used
accounts Fetch active accounts where account_type = 'asset', 'liability', or 'equity'
ledgers Get running balance for each account via LedgerService::getAccountBalance()
(Internal) Calls getProfitLoss() internally to include Net Profit/Loss in the Equity section

Generation Logic (Step by Step)

  1. ReportService::getBalanceSheet(financial_year_id) is called
  2. Queries accounts: WHERE account_type IN ('asset', 'liability', 'equity') AND is_active = 1
  3. For each asset account, gets balance from ledger
  4. For each liability account, gets balance from ledger
  5. For each equity account, gets balance from ledger
  6. Calls getProfitLoss() to get Net Profit/Loss
  7. Adds Net Profit/Loss to Equity total (Retained Earnings)
  8. Checks: Total Assets == Total Liabilities + Total Equity
  9. Reports whether the balance sheet is balanced or out of balance

What the Report Shows

Section Content
Assets All asset accounts (Cash, Bank, AR, Inventory, Fixed Assets, etc.) with amounts
Total Assets Sum of all assets
Liabilities All liability accounts (Loans, AP, Taxes Payable, etc.) with amounts
Total Liabilities Sum of all liabilities
Equity Capital + Net Profit/Loss + Other equity accounts
Total Liabilities + Equity Must equal Total Assets
Balance Status "Balanced" or "Out of Balance" with the difference

Generation Logic (Step by Step)

17.5 Account Ledger

Purpose Shows all transactions for a specific account with opening balance, running balances, and closing balance. The most detailed single-account report.

Tables Used

Table How It's Used
accounts Get account details (code, name) for the selected account
ledgers The PRIMARY table. Queries all ledger entries for the selected account:
WHERE company_id = ? AND account_id = ? AND transaction_date BETWEEN ? AND ?
Ordered by transaction_date ASC
vouchers Via relationship: voucher details linked to each ledger entry
financial_years To determine opening balance

Generation Logic (Step by Step)

  1. LedgerService::getAccountLedger(account_id, date_from, date_to) is called
  2. Fetches account details from accounts table
  3. Calculates Opening Balance:
    • Queries ledgers for the LAST entry before date_from
    • OR uses the account's opening_balance if no prior entries exist
  4. Fetches all ledger entries within the date range: WHERE account_id = ? AND transaction_date BETWEEN from AND to ORDER BY transaction_date
  5. For each ledger entry, reads:
    • transaction_date, voucher_id (via relationship: voucher number), description
    • debit, credit
    • running_balance (pre-computed)
  6. Closing Balance = last entry's running_balance
  7. Total Debit and Total Credit for the period

What the Report Shows

Column Description
Header: Account Code, Account Name
Opening Balance (before the date range)
Date Transaction date
Voucher # Linked voucher number
Description Transaction description
Debit Debit amount for this entry
Credit Credit amount for this entry
Running Balance Cumulative balance after this entry
Closing Balance | Total Debit | Total Credit

Filters

date_from No Start date (default: FY start)

20. Subscriptions & Billing

Subscription Plans (SuperAdmin Managed)

Plans are created at /admin/subscription-plans with these attributes:

Attribute Description
Name Plan name (e.g., "Starter", "Professional", "Enterprise")
Price Monthly/yearly price
Duration Billing cycle: monthly, yearly, or lifetime
Max Users User limit
Max Companies Company limit
Features List of included features
Is Active Enable/disable plan

Subscription Flow

  1. Company admin views plans at /admin/subscriptions/plans (web) or GET /api/v1/subscriptions/plans (mobile)
  2. Selects a plan and billing cycle (monthly, yearly, or lifetime)
  3. Free / trial plans: subscription activates immediately (HTTP 201) — no payment step
  4. Paid plans: POST /subscriptions/subscribe returns requires_payment: true and a checkout object (key_id, order_id, amount_paise, etc.)
  5. User completes Razorpay checkout (web popup or Razorpay mobile SDK)
  6. Client calls POST /subscriptions/verify-payment with razorpay_order_id, razorpay_payment_id, razorpay_signature
  7. Alternatively, Razorpay webhook (POST /webhooks/razorpay) confirms payment server-side
  8. Subscription is activated and invoice/payment records are created

Razorpay Integration

Add these keys to .env (see .env.example):

RAZORPAY_KEY_ID=rzp_test_xxxxx
RAZORPAY_KEY_SECRET=your_secret
RAZORPAY_WEBHOOK_SECRET=your_webhook_secret
  • Web admin: Razorpay Checkout JS popup on the plans page; verify via POST /admin/subscriptions/verify-payment
  • Mobile API: open Razorpay SDK with checkout fields from subscribe/change-plan, then call POST /api/v1/subscriptions/verify-payment
  • Razorpay Orders: razorpay_orders table
  • Razorpay Webhooks: razorpay_webhooks table (logs all webhook events)
  • Subscription Payments: subscription_payments table
  • Subscription Invoices: subscription_invoices table

Offline-First Mobile Flow

  1. First login: call POST /login with device_id, then GET /sync/bootstrap to cache master data locally (accounts, parties, items, categories, tax rates, bank accounts).
  2. Offline edits: save changes in local SQLite/storage with UUID + version; queue payloads for upload.
  3. Back online: call POST /sync/upload with queued entries (auto_process: true by default), then GET /sync/download?since=... for server-side changes.
  4. Manual sync button: call POST /sync/run anytime to process pending queue items and refresh status via GET /sync/status.
  5. Paid subscription: POST /subscriptions/subscribe → open Razorpay with returned checkout → POST /subscriptions/verify-payment on success.

Support & Notifications (Web + Mobile)

  • Tenant admin: Admin panel → Help & Support → create ticket, chat in thread, get notified in header bell.
  • SuperAdmin: Admin panel → Support Inbox → view all company tickets, reply, assign, change status; internal notes visible to staff only.
  • Mobile: same ticket APIs; poll GET /notifications/unread-count for badge count; mark read returns updated count.
  • Web header: notification bell loads feed via AJAX, polls unread count every 60 seconds, and updates badge dynamically.
